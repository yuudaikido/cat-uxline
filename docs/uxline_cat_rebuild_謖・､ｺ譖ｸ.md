## 2. アーキテクチャ仕様（マクロ）：UXライン

### 構造
```
[ジャーニーA] [ジャーニーB] [ジャーニーC]   ← Lines層（変わりやすい：体験）
      ↓            ↓            ↓
  共有サービス層（ドメインAPI＝業務ルール）   ← Domain層（変わりにくい：意味）
                  ↓
             データ層 / DB                 ← 最安定：事実
```

### 規則
- **切る単位＝ジャーニー**（ユーザーが目的を達成するまでの画面の流れ全体）。1機能や1画面ではない
- Lines層は **DB・Eloquentに直接触れない**。必ずDomain層のドメインAPIを経由する
- ドメインAPIは「意味」を公開し「形」を隠す（×「検針データをくれ」／○「この値は異常か？」）
- **共有ロジックの二分法（最重要の設計判断基準）**：
  - **事実系**＝ズレたら業務事故になるもの（料金計算・異常値定義・税計算等）。定義はシステム内に常に1つ。実装＝インターフェース契約＋DIバインド。切替はbind一行差し替え、全ライン一斉
  - **体験系**＝ライン都合で変えて無害なもの（表示丸め・並び順・通知の出し方等）。実装＝メソッド付きenum（Strategy）。変種を追加し、各ラインが自分のタイミングで乗換
  - 判定候補軸：「その値が下流の意思決定・計算に使われるなら事実系、表示のみなら体験系」
- **共通化はRule of Three**：1回目はライン内に書く。2回目はあえて重複。3例目が現れて初めてDomain層へ昇格

## 3. アーキテクチャ仕様（ミクロ）：CAT

「様式は存在しない。1つのノード集合と、N枚のグラフがあるだけ」

### 原理①：住所式命名
- 関数名形式：`名前_種別_連番`（例：`readData_seq_1`, `persistReading_tx_1`）
  - 種別タグ例：`seq`（順次処理部品）/ `tx`（トランザクション関与）/ `q`（クエリ）/ `fmt`（体験系整形）
- 一意性は規則が保証し、意味は **REGISTRY.md**（対応表）が持つ。全関数を1行1エントリで登録：
  `| 名前 | 所属（Line/Domain）| 一言の意味 | 入出力 |`
- REGISTRY.md の更新は関数追加と同一コミットで行う（陸腐防止）

### 原理②：オーバーレイグラフ
- 大域不変条件は基底コードに混ぜず、独立レイヤーとして上から敷く
- Laravelでの実装：ミドルウェア（認証・検証状態）、DBトランザクションラッパー、必要ならdeptracでレイヤー違反の静的検査
- レイヤー例：TX境界網 / 認可網 / 入力検証網

### 原理③：エッジ実体化（関係関数）
- 「常にこの順・このセットで呼ばれる」列は **関係関数** に昇格させる
- 部品関数（葉）は非公開（private / 内部専用）。上位は関係関数のみを呼ぶ → 誤順序を構造的に不可能にする
- 関係関数はネスト可（共有ありDAG）。上層＝純粋な組み立てのみ、葉＝純粋な仕事のみ
- 実行時文脈（トランザクション中か等）は関係関数の内側に置く（部品は文脈を知らない）
- 可変の後段は callable で受ける（`fetchParse_then($next)` 形式）

### 織り込み順序（猫の規則）
- 複数レイヤーの重ね順は定義側で固定せず、**観測点（呼び出し文脈）が確定**させる
- 頻出の重ね順は **関係レイヤー** として部品化して命名（例：`txOutsideRetry_rel_1`）。事故りやすい順（TX内リトライ等）は関係レイヤー経由でしか使えないようにする

## 4. フォルダ構造（構築先の骨格）

```
uxline-cat-lab/
├── docker-compose.yml          # php-lab方式（web + db）
├── REGISTRY.md                 # 原理①の対応表
├── ARCHITECTURE.md             # 本書の要約＋判断ログ
└── src/ (Laravel 12)
    ├── app/
    │   ├── Lines/                       # ── Lines層（ジャーニー単位）
    │   │   └── MonthlyReading/          # 例：月次検針ジャーニー
    │   │       ├── Http/                # Controller・Request
    │   │       ├── Relations/           # 関係関数（原理③）
    │   │       ├── Views/ (resources側でも可)
    │   │       └── Format/              # 体験系enum
    │   ├── Domain/                      # ── 共有サービス層
    │   │   ├── Contracts/               # 事実系インターフェース
    │   │   ├── Services/                # 現役実装
    │   │   └── Data/                    # データアクセス（Eloquentはここに封印）
    │   └── Overlays/                    # ── 原理②（ミドルウェア・TXラッパー・関係レイヤー）
    └── routes/web.php                   # ジャーニー単位にグループ化
```

## 5. 作業フェーズ（各フェーズ末で必ず停止し、報告→承認を待つ）

### Phase 0：調査とジャーニー抽出
1. 参照元の `routes/web.php`・`app/Http/Controllers/`・`app/Models/`・`database/migrations/` を読む
2. 画面遷移とユースケースから **ジャーニー候補を列挙**（3〜6本想定）
3. 各ジャーニーが触るデータと業務ルールを一覧化
4. 業務ルールごとに **事実系／体験系の分類表（判定理由つき）** を作る
- 成果物：`ARCHITECTURE.md` 内に「ジャーニーマップ」「事実系/体験系分類表」→ ここで停止・レビュー依頼

### Phase 1：骨格構築
1. 構築先にLaravel 12を新規セットアップ（docker compose、php-labと同ポート帯を避ける）
2. §4のフォルダ構造・空のREGISTRY.md・ARCHITECTURE.mdを配置
3. 参照元migrationsを識別情報除去のうえ移植し、migrate成功まで確認
- 成果物：ブラウザでLaravel初期画面表示＋migrate完了 → 停止・報告

### Phase 2：最重要ジャーニー1本の垂直実装
1. Phase 0で合意したジャーニーから **1本だけ** を選び（推奨：検針データの登録〜一覧の流れ）実装
2. 実装順：Domain層の事実系契約 → 現役実装＋bind → Lines層の関係関数DAG → Controller/View → 体験系enum
3. 全関数をREGISTRY.mdへ登録。関係関数の葉は非公開にする
- 成果物：1ジャーニーがブラウザで動作 → 停止・報告

### Phase 3：オーバーレイ敷設
1. TX境界・入力検証をOverlaysとして実装（基底コードに混ぜ込まない）
2. 重ね順が問題になる箇所を1つ意図的に作り、**関係レイヤーで解決**して例示
3. 可能ならdeptracで「Lines→Domain一方向・Lines→Eloquent直接参照禁止」を機械検査
- 成果物：オーバーレイ動作確認＋違反検査 → 停止・報告

### Phase 4：検証レポート
1. PHPUnitで事実系契約のテスト（契約テスト：インターフェースに対し実装横断で同一スイート）
2. `ARCHITECTURE.md` に総括を書く：うまくいった点／破綻した点／CAT・UXライン仕様へフィードバックすべき修正案（正直に。忖度した称賛は不要）
- 成果物：テスト結果＋総括レポート

- 事実系か体験系か迷ったら：勝手に決めず、両説と根拠を提示して質問する
- 参照元のロジックが理解できない場合：推測実装せず「不明」として印を付けて質問する
- 本書と原典Notionが矛盾したらNotionを優先し、矛盾箇所を報告する
- スコープ拡大禁止：Phase 2は必ず1ジャーニーのみ。全ジャーニー移植は本実験の目的外
